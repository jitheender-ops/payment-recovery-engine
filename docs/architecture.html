Payment Recovery Engine

An AI-assisted engine that recovers revenue stuck in failed payments and uncollected dues. It listens for Razorpay payment failures, accepts merchant-reported revenue-at-risk events, decides — through a deterministic-guardrailed LLM agent — whether, when and how to chase, and collects through Razorpay Payment Links, attributing every recovered rupee back to the attempt that earned it.

FastAPI · PostgreSQL · Razorpay · Anthropic/OpenAI · XGBoost fallback · Alembic · Streamlit dashboard

01What this system is

Money goes missing in two distinct ways, and the engine hunts both:

  • A payment was attempted and failed. A card charge declined, a UPI collect request timed out, a bank was down. Razorpay reports these through payment.failed webhooks — the engine classifies the failure, decides whether a retry can succeed, and re-presents the payment through a fresh Payment Link on the rail most likely to work.
  • No payment was ever attempted, but revenue is at risk. A cart was abandoned at checkout, a subscription renewal didn't go through, a B2B invoice is past due, a pre-approved mandate debit failed. These exist only in the merchant's own systems, so the merchant pushes them to the engine's /risks endpoint, and dedicated chasers pursue each type on its own policy: how many touches, how far apart, for how long.

Both kinds of money share one spine: a recovery case with a bounded attempt budget, an escalation ladder, a consent window, and a recovered amount. Recovery always goes out as a Razorpay Payment Link; when the customer pays it, a brand-new payment id is born, and the engine's attribution machinery joins that new payment back to the attempt that sent the link.

Headline question The whole design serves one metric: how much money did the engine recover, and which of its actions earned it? Every table, every audit event, and the distinction between recovered and recovered-via-our-attempt exists so that number is answerable and honest.

02Core design principle: Deterministic → LLM → Deterministic

The LLM is sandwiched between two deterministic layers. This is the single most important architectural decision in the system.

Deterministic · pre-LLM
  • HMAC signature verify
  • Idempotency / dedup
  • Event store
  • Error-code classifier
LLM · constrained
  • Policy agent
  • Fixed action space
  • JSON contract
  • Untrusted input labelled
Deterministic · post-LLM
  • Action schema validation
  • Business-rule guardrail
  • Idempotency key
  • Write-ahead, then execute
  • Pre-LLM determinism handles what a lookup table can solve. Calling an LLM to classify insufficient_funds from a structured error code would be wasteful and fragile — a YAML map does it in microseconds, identically, forever.
  • Post-LLM determinism is the safety net. The LLM may hallucinate; the guardrail validates every proposed action against hard business rules before anything touches money or contacts a customer. The guardrail checks all rules and reports all violations — no short-circuiting — so the audit trail shows the complete picture of every decision.
  • The LLM's action space is fixed and small: retry_now retry_at switch_rail nudge_customer abandon — it can propose, never invent.

03The two rails

Payment rail — webhook-driven

Trigger: Razorpay payment.failed webhook. A payment exists and has a payment_failures row behind the case. Retries can re-present a charge; switch_rail means "ask for the same money on a different instrument". Consent window: 72h from failure (global setting). Budget: 3 attempts.

payment_failure risk_type · failure classes from the deterministic classifier · capture attribution can also match on order_id (self-recovery).

Risk rail — merchant-driven (the chasers)

Trigger: merchant POSTs an HMAC-signed event to /risks. There is no payment behind the case — retry_attempts.payment_failure_id and .payment_id stay NULL. "Retry" therefore always means mint a Payment Link and deliver it; there is no silent re-present. Per-type consent windows (48h–720h) anchor at case open.

checkout_abandonment subscription_failure invoice_overdue mandate_failure

The two rails share everything below the trigger: one case table, one decision pipeline, one guardrail, one executor, one attribution machinery, one recovery page. risk_type says how the money went missing; subject_ref identifies it in that source's namespace (a payment id, a cart id, an invoice number, a mandate token). The pair is UNIQUE (uq_recovery_case_subject), which is what makes re-ingestion idempotent.

04Payment rail, end to end

1
Webhook arrives — verify, store, acknowledge
Razorpay POSTs to /webhooks/razorpay. The raw body's HMAC-SHA256 is checked against X-Razorpay-Signature before anything else. The event is stored (webhook_events, deduplicated by Razorpay event id) and the endpoint returns 200 in <10ms. All real work runs in a background task — the gateway must never be kept waiting, and a slow consumer must never cause redeliveries.
src/ingestion/router.py · src/ingestion/signature.py · src/ingestion/idempotency.py
2
Classify the failure — deterministically
Razorpay's 5-tuple error codes map through an in-memory YAML table onto a failure taxonomy: insufficient_funds, bank_downtime, network_error, upi_collect_timeout, 3ds_dropoff, issuer_decline, card_limit_exceeded, payment_timeout, plus the non-retryables hard_decline, fraud_block, customer_cancelled, invalid_card, expired_instrument. Each class carries an is_retryable verdict. No LLM is involved.
src/classifier/mapper.py · src/classifier/taxonomy.py · src/classifier/error_codes.yaml
3
Open (or find) the recovery case
Get-or-create on (risk_type, subject_ref). Re-ingesting the same failure lands on the existing case — a second case for one payment would double both the attempt budget and the recovered amount. The UNIQUE constraint plus an IntegrityError re-fetch closes the race between concurrent webhooks.
src/cases.py::open_case
4
Hard decline? Abandon without an agent call
Fraud blocks, customer cancellations and broken instruments fail again by definition. Retrying them would burn money and goodwill against the same wall — the case closes as abandoned deterministically, and the LLM is never consulted.
src/orchestrator.py::process_payment_failure
5
Build context, ask the policy agent
A FailureContext captures the facts: failure class, amount, rail, hour-of-day and weekday in IST, retry/nudge counts in the last 24h, consent window. The LLM policy agent answers with a constrained JSON action. Gateway error text rides in as untrusted data, explicitly labelled not-instructions in the prompt.
src/agent/actions.py · src/agent/policy_agent.py · src/agent/prompts.py
6
Guardrail validates the action
Every rule runs, every violation is reported: action schema, hard-decline blocklist, consent window, attempt budget, per-customer contact limits, IST blackout (23:00–07:00), amount ceiling. A rejected action is recorded as a rejected attempt — the audit trail keeps the decision, the customer never feels it.
src/guardrail/gate.py · src/guardrail/rules.py
7
Write-ahead, then execute
The attempt row is committed before the Razorpay call, never after — a crash between API call and commit must leave a recorded unknown, not a vanished charge. The executor mints the Payment Link (UPI-only when the rail switch is to UPI, with graceful fallback), carries the personalized nudge as the link's checkout description, and notifies by SMS/email. The link id is stored as external_ref — the attribution join key.
src/orchestrator.py::_execute_and_record · src/executor/retry_executor.py
8
Money comes home — attribute the capture
When the customer pays the link, Razorpay sends payment.captured with a brand-new payment id. The engine joins it home through the link id, the idempotency-key breadcrumb in the link's notes, or the order id (self-recovery — money counts, engine takes no credit). The case closes as recovered; late payments on terminal cases are logged as overpayments for manual refund, never double-credited.
src/cases.py::attribute_capture
Latency budget Signature <1ms · idempotency <5ms · classification <1ms · LLM agent <3s · guardrail <1ms · nudge generation <3s (3s timeout, template fallback) · Razorpay call <2s. Total <10s, fully async — the webhook itself answers in milliseconds.

05Risk rail, end to end

1
Merchant pushes a risk event
POST /risks with X-Risk-Signature (HMAC-SHA256 over the raw body, same discipline as the Razorpay webhook). Schema boundaries are honest: amount is capped at the 32-bit paise ceiling, currency is INR-only (the whole customer-facing stack — ₹ display, UPI rail, IST blackout — assumes rupees), malformed JSON gets a clean 400. With RISK_WEBHOOK_SECRET unset, every event is rejected — the surface is closed until configured on purpose.
src/ingestion/risk_router.py
2
Store, deduplicate, acknowledge
The event lands in risk_events with a deterministic dedup key — the merchant's event_id when supplied, otherwise derived from (risk_type, reference_id, occurred_at). A redelivery collides onto the same key and the UNIQUE constraint turns it into a clean 200. The response returns immediately; processing runs in the background.
src/models.py::RiskEvent
3
Open the case with the type's policy
The per-type policy supplies the attempt budget, the consent window, and the first-touch time. The case opens with next_action_at set — that is the handle the scheduler's sweep grips, since risk types have no inbound webhook to re-trigger them.
src/orchestrator.py::process_risk_event · src/chasers/policy.py
4
Immediate types chase at ingestion; deferred types wait
Invoices and subscription failures act immediately (first_action_hours = 0) — the first chase runs right inside the background task. Carts wait 1h and mandates 24h: their first touch is parked on next_action_at and picked up by the chase sweep. Before any chase, three gates: the stopping rules, the consent window (a case past its window closes as expired), and the IST blackout (a chase during quiet hours defers to the window's edge without spending an attempt).
src/orchestrator.py::chase_case
5
Decide → guardrail → deliver
The same decision pipeline as the payment rail, with one semantic difference: every non-abandon action delivers the link. A risk case has no instrument to re-present silently, so a "retry" that nobody is told about would be a dead chase reporting success. The nudge message is generated for every action — with risk-aware wording, because three of the four types never attempted a payment and the customer must never be told one failed.
src/orchestrator.py::_execute_case_and_record · src/messaging/nudge_generator.py
6
The ladder climbs until money, budget, or window ends it
Each touch pushes next_action_at out by the type's re-chase interval; the escalation backoff widens the gap per rung. A capture closes the case as recovered; a spent budget closes it exhausted; a passed window closes it expired; an opt-out closes it opted_out — forever.
src/cases.py · src/scheduler.py::chase_due_cases

06The decision pipeline

One function — _decide_action — serves every decision path (live webhook, chase sweep, fired retry), so the distinction between "who was configured to decide" and "who actually decided" lives in exactly one place.

The degradation chain, and why it is watched

A
LLM policy agent
Proposes an action with reasoning and confidence. Its output must pass schema validation; gateway text in the prompt is fenced as untrusted data.
B
Silent-degradation detector
PolicyAgent.decide() never raises — it swallows LLM errors and returns its own private heuristic. "An agent object exists" therefore says nothing about whether the LLM answered. The orchestrator compares the agent's fallback_count across the call: if it moved, the LLM degraded, and its private heuristic (which abandons ~70% of recoverable payments) is refused.
C
XGBoost baseline / rule-based heuristics
A trained model when one exists for the failure class; deterministic per-class rules otherwise (and always for the four risk classes, which are ours, not the gateway's). This layer is what the audit trail records as agent_type = "xgboost" — the trail says who actually decided.

The self-serve subset is deliberate, and documented in code: the rules that bound our outreach fall away when the customer initiates; the rules that protect the money (schema, blocklist, window, budget, idempotency) never do.

07Money-safety invariants

Invariant 1 — Write-ahead The attempt row is committed before the Razorpay call, on every path that moves money. Recording it afterwards leaves a window where money has moved and nothing in the database says so: a crash there would vanish the attempt, free the idempotency slot, and let the next event charge the customer twice. Committing first makes a crash a recorded unknown, which the stale-attempt sweep resolves fail-closed. This ordering is a correctness property, not a style choice — it is duplicated nowhere and reordered never.
Invariant 2 — Deterministic idempotency keys retry_{payment_id}_{attempt} · chase_{risk_type}_{ref}_{attempt} · selfserve_{ref}_{attempt}. The keys are derived from facts, not generated, and retry_attempts.idempotency_key is UNIQUE. Two workers racing on the same case both compute the same key; the constraint lets exactly one through before Razorpay is called. The loser rolls back and logs the race.
Invariant 3 — Reuse, never re-mint While an attempt's link is live, the customer page sends them back to the existing link instead of creating another. Every retry otherwise mints a NEW link while old ones stay payable on Razorpay's side — the classic double-pay setup. When a case reaches a terminal state, a sweep cancels every link it spawned, so nothing can be paid late.
Invariant 4 — Never chase a pending attempt If the latest attempt is still unresolved, the case is untouched — offering another payment while one is in flight is how a customer ends up paying twice. Stale pendings (crash mid-call) are resolved fail-closed after 15 minutes by the reconciliation sweep.
Invariant 5 — Fail closed everywhere Unset secrets reject all traffic (webhooks, risk events, recovery pages). Unknown states resolve against acting. A link whose status cannot be confirmed renders as unknown and refuses the pay button rather than guessing.

7.1 Revenue attribution — joining new money home

Recovery goes out as a Payment Link; the payment that eventually succeeds carries an id the engine has never seen. attribute_capture resolves it, most specific first:

#Match onMeaningCredit
1link_id → retry_attempts.external_refThey paid the exact link we sentEngine's recovery
2notes.retry_idempotency_key → idempotency_keyRazorpay copies link notes onto the payment; the breadcrumb the executor wrote joins it home even if the link id is missingEngine's recovery
3order_id → the case's subject (payment rail only)The customer paid on their own, no link of ours involvedMoney counts, recovered_via_attempt_id stays NULL — the headline never takes credit for the control group

A capture matching a terminal case is an overpayment — a superseded or orphaned link paid late. It is logged loudly as an overpayment event for manual refund and nothing is credited twice. On attribution, every still-pending attempt on the case is marked superseded: the money arrived, further action is moot.

08Case lifecycle

recovery_cases is the centre of the schema, not payment_failures. A failed card charge, an abandoned cart, a halted subscription, an overdue invoice and a dead mandate are all money we might get back; they differ only in how they were detected. One case table, one attempt budget, one set of terminal states, one recovered-amount column — not five parallel pipelines.

openMoney at risk, budget remaining, chaseableopen_case

The three stopping rules, and where each lives

RuleColumnEnforced by
Attempt budget spentattempts_used / max_attemptsstop_reason()
Consent withdrawnretry_ledger.consent_statusstop_reason() — never expires
Contact not yet duenext_action_atstop_reason() — expires on its own

next_action_at is written by two things: the escalation backoff in attach_attempt() (24h × escalation level — the gap widens per rung), and a promise-to-pay, which takes the later of the promise date and whatever the ladder had already scheduled. A promise is permission to wait, not permission to contact sooner. A broken promise pulls next_action_at back to now rather than NULL — NULL means "a webhook is this case's trigger", and clearing it would release the case into a queue nothing reads.

Every transition is written to case_events — opened, contacted, escalated, deferred, stopped, attributed, closed — with the actor (system, agent type, customer, scheduler) and a JSON detail payload. The audit trail is not a by-product; it is the evidence that the headline number rests on.

09The four chasers

Each risk type is a policy record — bounds, not scripts. The agent decides inside them; the guardrail enforces them; the sweep executes to them.

Risk typeMax touchesConsent windowFirst touch Re-chase everyPreferred railFailure class (ours)
checkout_abandonment248h+1h 24h—abandoned_checkout
subscription_failure4168h (7d)immediate 24hUPIsubscription_charge_failed
invoice_overdue4720h (30d)immediate 72h—invoice_overdue
mandate_failure3168h (7d)+24h 48hUPImandate_debit_failed

The character of each chase, as taught to the policy agent:

  • Abandoned cart — a cold cart chased twice is spam. One gentle nudge with the link is the whole play; if a nudge already went out, abandon.
  • Subscription renewal — treat like a payment failure on an unknown rail; renewals usually die on card OTP drop-offs, so prefer UPI.
  • Overdue invoice — the counterparty is a business contact. Keep the ladder slow (72h rungs); a promise-to-pay pauses the chase until its date passes.
  • Failed mandate — the mandate is standing consent to collect, so re-presenting next day is usually right; space the touches, because every touch delivers a link.
Copy discipline Three of the four types never attempted a payment, so no customer-facing surface — nudge prompt, fallback template, recovery page — may say "payment failed" for them. The LLM nudge prompt is told the situation per type ("an order was left incomplete — no payment was attempted"), the fallback templates are written per class, and the page renders per-type heroes.

10Scheduler & sweeps

A single tick every 60 seconds (configurable) runs the sweeps in a fixed order, stamps a heartbeat, and commits. The fire and chase sweeps share one time budget — a fraction of the tick interval — so back-to-back sweeps can never run the tick long past the interval, stale the heartbeat, and delay deferred work.

OrderSweepWhat it does
1fire_due_retriesFires parked retry_at attempts (both rails) whose time has come. Re-validates case state and consent at fire time, re-runs the guardrail, then executes. Claims are atomic — a conditional UPDATE only lands while the row is still pending.
2reconcile_eventsRe-runs webhook events whose background task never finished (restart, crash, deploy in the 200-to-task window). Re-arms failures up to a cap, then rests them with the error recorded.
3reconcile_risk_eventsThe same safety net for /risks events — the only retry mechanism there is, since merchants don't re-deliver after our 200.
4reconcile_stale_attemptsResolves attempts pending for >15 minutes. Crash before the write-ahead phase → re-parked as scheduled; crash after → resolved fail-closed as failed. Razorpay is never re-called blind.
5cancel_links_for_closed_casesKills the Payment Links of terminal cases so they can never be paid late. Already-inert links resolve as success on the first pass; failed cancels retry next tick.
6expire_promisesPromises-to-pay whose date passed with no money → broken; the case's next_action_at returns to now and the chase resumes.
7chase_due_casesThe chaser sweep: all four risk types in one oldest-first query, each case through chase_case until the shared time budget runs out, then yields — the rest waits for the next tick rather than starving it.
8report_due_casesCounts payment-failure cases still waiting on their next webhook — after the chase, so it reports only what the chase left behind.

10.1 Self-healing, or: what happens when things die

The system assumes every component can fail mid-step, and each failure mode has a named recovery path:

11Customer-facing surface

One page — /recover/{token} — answers the question every arriving customer has: "has my money already gone?" before asking for any more. The token is signed, expiring, and scoped to a single case; with RECOVERY_LINK_SECRET unset every token is rejected. The page is deliberately not behind API-key auth — its reader is a member of the public who just had a payment problem.

The seven view states

One function derives the customer-visible state so the template branches once and the ordering is reviewable in one place:

StateCondition (in check order)Pay button?
recoveredCase recovered, or amount_recovered ≥ amount_at_riskNo
opted_outCustomer asked us to stopNo
confirmingAn attempt went out and hasn't resolved, <15 min old — checked before payable: offering payment here is how double-pays happenNo
unknownSame, but older — admits it cannot confirmNo
stoppedExhausted / abandoned / expired, or the consent window passed (backstop for a window crossing no sweep has seen yet)No
not_retryableHard decline — retrying would hit the same wall; the page says soNo
payableEverything else — amount, reassurance, one pay buttonYes

Self-serve pay

The pay button POSTs to /pay: a guardrail subset runs (schema, blocklist, consent window, budget, idempotency — not blackout or contact limits, since the customer initiates), a write-ahead row with key selfserve_{ref}_{attempt} closes the double-tap race, the link mints, and the customer is redirected straight to Razorpay — not notified about their own click. If the link already exists and is live, they go back to it.

Honesty, language, and trust

  • Risk-aware copy. Per-type heroes ("This invoice is past due", "Your order is still waiting"), per-type timelines, and the payment-only FAQ ("I was charged, but this page says failed") renders only where a payment was actually attempted.
  • English + Hindi from one key catalog with cross-language fallback; every template key exists in both.
  • The merchant's name is the trust anchor in any message asking for money — an unnamed link reads as phishing. Unset, it falls back to a neutral phrase rather than blocking the send.
  • Opt-out is one click, closes every open case for the customer, and the ledger remembers it forever.

Untrusted input discipline

  • Gateway error text (Razorpay's descriptions) enters the LLM prompt fenced as data-not-instructions.
  • Merchant meta on risk events passes through one funnel — sanitize_meta — reduced to a bounded map of printable strings; nested structures are stringified rather than flattened, so they can't widen the injection surface. The prompt labels the block untrusted.
  • Merchant-typed contact data is shape-checked at the executor funnel; a misshapen email or phone is dropped (with a logged warning) and the link mints without prefill — a typo must not be able to kill a chase.
  • Nudge templates render with Jinja2 autoescape on — customer-controlled fields cannot smuggle markup into message bodies.
  • Secrets live in the environment, never in the repo; .env* is gitignored. Assertion failures are written never to render settings (which would print key ids into CI logs).

15Observability

  • Heartbeat — every tick stamps scheduler_heartbeat with its counts (retries fired, events reconciled, cases chased, links cancelled, promises expired…). The dashboard's Operations view renders it as Scheduler alive / STALE against a 3-minute freshness bound.
  • Audit trail — case_events records every transition with actor and detail: the evidence behind every recovered rupee and every abandoned case.
  • Attempt rows as telemetry — agent_type (who decided), guardrail_passed + rejection reasons (what was checked), result (what happened), rail_fallback (was the rail switch downgraded), channel (what actually reached the customer — not what was intended).
  • Dashboard views — recovery funnel (failed → retryable → contacted → recovered), bank breakdown, case register with promises and events, operations panel, eval results.
  • Structured logs at every money-moving step: link ids, idempotency keys, race outcomes, fallback triggers, overpayments (at WARNING, refund-required).

    --capture-rate 0.5 --seed 42                              # the four chasers

# 5. See the pages
.venv/bin/python scripts/recovery_links.py                    # one URL per page state

# 6. Verify
.venv/bin/ruff check src eval scripts tests

.venv/bin/python -m pytest -q
.venv/bin/python scripts/check_migrations.py

Production deploys to Render with a managed PostgreSQL (render.yaml); the migration chain runs at boot and the scheduler runs in-process with the API.

Known gaps (documented, deliberate)

  • Promises-to-pay have no production entry surface yet — the plumbing (record, pause chase, expire, resolve on capture) is built and tested; wiring an inbound channel is future work.
  • Hindi copy needs native review before real sends.
  • The offline eval harness covers the payment rail; chaser-specific evaluation is future work.
  • Voice/WhatsApp channels are modeled in the channel enum but not shipped — SMS/link is the live channel.
